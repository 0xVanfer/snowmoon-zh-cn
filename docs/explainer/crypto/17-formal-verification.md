# 17 形式化验证（Formal Verification）

> 一句话定义：**形式化验证**是把"程序应该做什么"写成数学命题，再用一个机器检查器去证明"程序做的确实是这件事"——不是测了一万次都没出事，而是对**所有**输入都成立。

---

## 1. 它是什么

把一段程序（或一份硬件设计）翻译成数学对象，然后证明一条定理：「在任意合法输入下，这段程序的输出满足规格说明写下的所有性质」。

和测试的根本区别只有一句话：

- **测试**证明的是「某些输入下没出错」；
- **形式化验证**证明的是「**所有**输入下都满足这条性质」。

这件事的现实困难在于：输入是无限的。你不可能穷举。所以真正的工作量不在"证明"，而在**找到一组足够强的抽象，把无限的输入空间压成有限的状态，并且让这条性质在这个抽象下依然成立**。

## 2. 小说里它在干什么

《雪月》把形式化验证当成泽国能活下来的技术底座。

**它是国家级防线。** 泽国没有钱做专有研发，但擅长照着开源方案造和改进：

> 「我们把编程语言和形式化验证做到了这样的程度」
> （第10章，chapter-10.md:295）

上下文是"设备代码里基本不再有能让外人从外部夺取控制权的严重错误"——注意这句话的**范围限定**：不是"没有 bug"，是"没有**能让外人从外部夺取控制权**的严重错误"。形式化验证的价值从来不是消灭所有错误，而是消灭那一类最致命的错误。

**它保护的是核心算法的机密性。** 第 27 章里，银聊用混淆电路保护用户消息，泽国这边声称持有**一份可机器检验的数学证明**：

> 「混淆电路算法满足标准的正确性与隐私性质」
> （第27章，chapter-27.md:209）

而且覆盖面是完整的：

> 「这份证明是端到端的，从操作系统一路覆盖到硬件」
> （第27章，chapter-27.md:209）

**但它诚实地划出了自己的边界。** 这句话是整篇里最重要的：

> 「除非哈希被攻破，否则零信息泄露」
> （第27章，chapter-27.md:209）

形式化验证只能证明「**在某些假设成立的前提下**，性质成立」。它不能证明那些假设本身。这里它把整个证明**归约到了一句话**：假设哈希函数不被攻破。这不是漏洞，这是形式化验证的正常输出形态——**把一个庞大的、无法穷尽的安全论证，压缩成少数几条可被独立质疑的假设。** 这恰恰是它的价值所在。

**它还承担了"抵抗新型攻击"的部分。** 泽国在向维里迪亚卖摄像头时声称：

> 「能传什么、不能传什么都写死在里面」
> （第32章，chapter-32.md:67）

"写死"对应硬件与代码里的硬性保证。第 5 章描述的那套「硬件认证和随机红外扫描」（第5章，chapter-05.md:157）就是它的执行方式：不是相信厂商的说明书，而是让第三方可以独立验证"它跑的程序确实是它声称的那个"。

**它还承认了自己有盲区。** 塞拉在第 32 章说：

> 「语言模型永远会以普通软件所不具备的方式被攻击」
> （第32章，chapter-32.md:65）

这解释了为什么第 10 章说"编程语言**和**形式化验证"要一起做：语言模型的行为不能像普通程序那样被完全规范化（它对提示词、采样随机性、训练数据的依赖无法被静态写死），所以那一部分只能靠别的手段兜底。

**书里还有第二条路线：差分测试。** 穆对那份证明并不完全放心，他用了一种"避嫌"的办法——

> 「我让翡翠去读原始学术论文，让它自己写一份实现」
> （第27章，chapter-27.md:211）

> 「再让一个全新的实例把那份代码和原版并排读」
> （第27章，chapter-27.md:211）

这在计算机科学里叫**差分测试（differential testing）**：不要求证明，只要求**两个独立实现对同一输入给出相同输出**。它和形式化验证是两条不同但互补的路，详见第 6 节。

## 3. 直觉：一个生活化的比喻

**测试 vs 证明，就是"抽查 n 个点"vs"证明多项式恒等于零"。**

数学上有这么一件事：两个多项式如果在**无穷多个**点相等，那它们处处相等。所以对多项式来说，"验证 1000 个点"其实**已经很强了**——但它仍然只是"很强"，不是"证明"，因为你可以人为构造出两个只在有限个点上不同的多项式（第 7 节有可运行的例子）。

而对**程序**来说更糟：函数的取值不是多项式，没有任何"有限个点定死了它"的性质。哪怕你测了一万亿次，也总有一个输入是你没测过的。

**所以形式化验证真正的机制不是"测更多"，而是"换一套更省输入的语言"。**

想象你要证明「这栋楼每一层都有消防通道」：
- **测试** = 抽查 100 层，每层都找到了消防通道 → 结论："抽到的都有"。
- **形式化验证** = 先证明「楼层编号满足一条规则：连续、到顶」，再证明「规则 ⇒ 每层都有消防通道」→ 结论："**所有**层都有"，包括你没去过的那些。

这就是**归纳不变式**的全部意义：**你不需要遍历无限的东西，你只需要证明"每一步都保持某个性质"，而这个性质保证你永远不会走丢。**

## 4. 原理

### 4.1 三个要素，缺一不可

| 要素 | 是什么 | 出错的后果 |
| --- | --- | --- |
| **规格说明（Specification）** | 用某种逻辑写清楚"应该怎样"。包括前置条件、后置条件、不变式 | **规格错了，证明白证**（见 6.1） |
| **语义模型（Semantics）** | 程序或硬件的数学模型——它的状态、状态转移、观测方式 | 模型和实物对不上，结论无效 |
| **机器检查器（Proof assistant）** | 一个小型可信内核 + 一堆证明脚本。Coq、Isabelle、Lean、TLA+ 等 | 内核有 bug，全盘失效 |

**这三者环环相扣，而最脆弱的通常不是第三个。** 人们直觉上以为"机器检查过的证明不会错"，但真正常见的失败模式是**规格写错了**或**模型与现实脱节**——而不是检查器算错了。

机器检查器做的是一件很笨的事：它只相信一个极小的、可信的**逻辑内核**（通常几百到几千行代码），其余全部是交给它检查的证明脚本。所以"证明"这件事被切成了两半：

- 极小的、必须绝对可信的内核（trusted kernel）；
- 巨大的、需要人写但可被完全机械检查的证明脚本（可替换、可独立审计）。

这个切分是整个领域能够规模化的关键——**你不需要信任任何人，只需要信任那个小内核。**

### 4.2 难点一：状态空间爆炸

设程序有 $n$ 个内存单元，每个是 1 比特。状态数是 $2^n$。真实程序有几十万个单元，状态数是 $2^{10^5}$ 这个量级。**穷举状态空间是彻底不可能的。**

所以实际做法不是"遍历所有状态"，而是**抽象**（abstraction）：

- 把与性质无关的细节**抽掉**（比如只关心数组长度，不关心每个元素的精确值）；
- 用**不变式（invariant）**描述"任何时刻都必须为真的性质"，并**证明每一步状态转移都保持它**；
- 只在**少数几个关键位置**（循环入口、出口、断言点）去检查这个不变式。

举例：要证明「求平均值的函数在输入非空时返回正确均值」，不需要枚举所有非空数组。你只要证明一条不变式：

$$\text{在第 } i \text{ 次迭代后：}\; s_i = \sum_{j<i} x_j \;\;\wedge\;\; i \le \text{len}$$

这个不变式在 $i = 0$（空和为 0）和每一步（加上 $x_i$）都成立，于是**对任意长度、任意取值**都成立。前提"非空"保证了最后一步 $i = \text{len} > 0$，除法合法。

**这就是从"无限输入"跳到"有限论证"的那一步。**

### 4.3 难点二：并发与分布式

单线程程序的不变式好写。多线程就麻烦了，因为"某时刻的状态"本身需要定义（有没有内存序？要不要线性化？）。

**TLA+** 是 Leslie Lamport（Paxos 的提出者之一）为此设计的：用集合论和时序逻辑写**行为规格**，然后用模型检查器把状态空间穷举一遍。Lamport 推广到 AWS 后，TLA+ 被用来推理 S3 和 DynamoDB 的并发模型，并在设计阶段找出了真实设计缺陷。**这是"用规格找 bug"最著名的案例**——注意它找 bug 的方式和形式化验证证明代码不同：它不证明"没 bug"，而是"把所有可能执行序列穷举一遍，看有没有一条走到不该到的状态"。

TLA+ 的模型检查之所以可行，恰恰因为**它只探索规格层面的状态（不是真实内存的每个比特）**。它证明的是"规格里没有矛盾"，不是"代码是对的"。

### 4.4 全栈证明链与可信计算基

第 27 章 209 行那句「从操作系统一路覆盖到硬件」，在术语上叫**全栈证明链（end-to-end proof chain）**：一个可验证执行环境（VEE / TEE）的安全性，是由一连串相互衔接的证明叠出来的。

典型结构（自下而上）：

```
┌─────────────────────────────────────────┐
│ 应用程序        语言级证明 / 类型系统      │  ← 「这 100 行代码符合规格」
├─────────────────────────────────────────┤
│ 运行时与操作系统  度量值 + 虚拟机证明      │  ← 「OS 没被偷偷换掉」
├─────────────────────────────────────────┤
│ 证明系统        内存隔离、度量链证明        │  ← 「我信任的代码之外的内存读不到」
├─────────────────────────────────────────┤
│ 硬件 + 固件     可信启动 + 硬件证明         │  ← 「从第一条指令起就没被换过」
└─────────────────────────────────────────┘
```

**中间任何一环断了，整条链就断了。** 上层证明得再漂亮，如果下层的度量值可以被伪造，那上层的"我跑的是这段代码"就是空话。

因此有一个关键概念：**可信计算基（TCB, Trusted Computing Base）**——链条上**没有被证明覆盖**的那一部分。TCB 越小越可信。seL4 之所以重要，正是因为它把 TCB 从"整个操作系统"缩小到"一万行左右的微内核"，而这一万行有完整证明。

**同时要注意：TCB 再小也永远不为零。** 至少还包括：CPU 本身、证明工具的可信内核、以及人在写规格时的判断。这就是为什么第 27 章会那样谨慎地划出"除非哈希被攻破"这个前提。

### 4.5 第二条路线：差分测试

穆在第 27 章 211 行的做法是差分测试。它的逻辑完全不同：

| | 形式化验证 | 差分测试 / 模糊测试 |
| --- | --- | --- |
| 问的问题 | "这段代码在所有输入下都满足 P 吗？" | "这两个独立实现会给出相同结果吗？" |
| 输出的结论 | **正面保证**（上界）：不会出现某类错误 | **负面发现**：找到一个反例 |
| 找不到反例时 | 真的给出了保证 | **什么都没证明** |
| 成本 | 高（需要写规格、不变量、证明脚本） | 很低（写个随机输入生成器就能跑） |
| 适用 | 长期运行、错误代价高的小核心代码 | 大规模、快速找 bug 的主力工具 |

**它们是互补的，不是竞争的。** 差分测试的强项恰恰是形式化验证的盲区：差分测试**不需要知道程序"应该"做什么**，它只需要另一个"参考实现"。所以它能用来检验"这个刚写出来的实现和已经被广泛验证过的老实现行为一致吗"。

**CompCert 论文正是同时用这两条路线**：它的核心（编译器从 C 到汇编的翻译）是机械证明的；它的后端则是用随机生成的程序做差分测试，与 GCC 的输出对比。这样既拿到了保证，也拿到了工程上的信心。

**一个诚实的补充**：差分测试的力量来自两个实现的**独立性**。如果 AI 读的论文和 AI 写的实现共享同一个误解（第 27 章 211 行的场景），测试就发现不了。穆让"一个全新的实例"来并排比对，就是在试图增加独立性——但这毕竟不是数学意义上的独立性。

## 5. 关键参数与真实世界的取值

**现实世界里跑通的项目（可独立核实的里程碑）：**

| 项目 | 验证对象 | 工具 | 备注 |
| --- | --- | --- | --- |
| **CompCert** | C 编译器的正确性 | Coq | 生成代码与源程序语义一致；seL4 的 x86_64 内核用 CompCert 编译 |
| **seL4** | 微内核（C 实现与汇编、链接脚本） | Isabelle/HOL | 第一个有完整机器检验证明的微内核；TCB 缩到约一万行 C 的量级 |
| **TLA+ 规格** | 分布式协议与并发模型 | TLA+ / TLC | 广泛用于描述 S3、DynamoDB 等系统的并发模型 |
| **Lean 4 + mathlib** | 数学定理 | Lean | 目前规模最大的形式化数学库之一，也是自动定理证明研究常用的基准 |
| **Frama-C / ACSL** | C 代码的逐函数性质 | 多种后端 | 工业界在用的"按规格逐函数检查"工具链 |

**关键的量级对比**：seL4 的证明规模比被验证的代码大一到**两个数量级**。这是形式化验证的真实成本——**证明的体量通常是代码的十倍到百倍**。这也是为什么它只被用在"错误代价极高、且体量小"的核心上（内核、密码学库、编译器、飞控），而不是整个应用层。

**逻辑系统的选择（大致对应可信度递减 / 自动化程度递减）：**

| 手段 | 保证强度 | 自动化程度 | 典型用途 |
| --- | --- | --- | --- |
| 依赖类型 / 精化类型（Liquid Types、F*） | 强 | 中 | 函数级性质，接近零成本 |
| 定理证明器（Coq / Isabelle / Lean） | 最强（可归约到极小内核） | 低 | 全程序、最强保证 |
| SMT 求解器（符号模型检查） | 中（只覆盖可判定的片段） | 高 | 局部性质、位级运算 |
| 模型检查（TLC、SPIN） | 只覆盖穷举到的状态 | 高 | 并发协议、找反例 |
| 抽象解释（静态分析） | 保守（会有误报） | 高 | 全代码扫描，简单的安全属性 |
| 差分 / 模糊测试 | 无保证（只找反例） | 很高 | 发现 bug 的主力 |

## 6. 容易误解的地方

**误解一：「验证通过了，程序就是对的。」** ❌ — 这是最贵的一个误解

形式化验证保证的是「**代码符合规格**」，不是「**规格是对的**」。业界把这两件事分别叫 verification（验证：代码符合规格）和 validation（确认：规格符合意图）。

真实存在的失败模式叫 **specification error（规格错误）**：你花了三年证明了「程序绝不会除以零」，而真正的 bug 在隔壁。

**这正是第 27 章那句话的重量所在**：

> 「除非哈希被攻破，否则零信息泄露」
> （第27章，chapter-27.md:209）

一份诚实的证明**必须**在开头把假设写清楚。这句话不是免责声明，是证明的**结论部分**——它告诉你这份保证的精确边界在哪，以及攻击者应该从哪里下手。**一份不声明任何假设的"形式化证明"，几乎肯定是错的。**

**误解二：「形式化验证能证明密码学是安全的。」** ❌
不能。形式化验证可以把「这个协议满足零知识性质」归约到「大整数分解是困难的」这类假设上，但它**无法证明这个假设为真**。第 27 章把整条链压缩到"哈希不被攻破"，是因为那正是当时他们能给出的最强结论。**密码学里的"证明"，严格来说是"条件证明"（conditional proof）。**

**误解三：「形式化验证比测试更高级，所以更该优先用。」** ❌
两者解决不同问题：
- 验证擅长**长期运行、错误代价高、体量小**的核心（内核、密码学、编译器、飞控）；
- 测试擅长**快速、大规模地发现**问题。

一个现实建议：**先测出 bug，再决定哪些部分值得证。** 很多团队的做法是先用 fuzzing / 差分测试把明显的洞堵上，再对剩下的、逻辑最关键的核心做证明。

**误解四：「AI 写证明，形式化验证要被取代了。」** ⚠️
第 27 章 211 行的场景（让 AI 读论文、写实现、并排比对）本质上是**自动化**了第 5 节表里那些"低保证、高自动化"的一格，而不是凭空消除了"规格从哪来"这个最难的问题。**自动证明器可以帮你找到证明，但写不出正确的规格。** 而且 Lean 这类形式化系统本身就是自动证明研究的主要基准——它的规模化恰恰是建立在"人给出结构和引理骨架、机器填缝"这个模式上的。

**误解五：「TCB 足够小，就安全了。」** ⚠️
TCB 小是相对的好消息，但：证明工具的可信内核在 TCB 里；CPU 的微架构（含缓存时序侧信道）在 TCB 里；**人在写规格时的理解也在 TCB 里**。第 32 章那句「语言模型永远会以普通软件所不具备的方式被攻击」（第32章，chapter-32.md:65）说的就是后两者之一：有些东西根本没法被静态写死。

**误解六：「形式化验证过的代码不会有 bug。」** ❌
它不会有**规格覆盖到的那类** bug。规格没写的，它一样有。这正是模型检查和差分测试必须和证明一起用的原因。

## 7. 自己动手试试

**实验一（数学版）：1000 个点全过，不等于证明。**

```python
import math
def f(x): return x**3 - 3*x**2 + 3*x - 1

def g(x):
    # g(x) = f(x) + (x-0)(x-1)(x-2)...(x-999)
    p = 1
    for i in range(1000):
        p *= (x - i)
    return f(x) + p

# "测试"：在 0..999 这 1000 个点上逐一比对 —— 全部通过
same = sum(1 for x in range(1000) if f(x) == g(x))
print("1000 个整数点上相等的个数:", same)      # 1000 —— 测试"全过"

# 但它们不是同一个函数
print("x=1000 时 f =", f(1000))
print("x=1000 时 g =", g(1000) % 10**18, "(末尾省略)")
print("结论：f 与 g 相同吗？", f(1000) == g(1000))   # False
```

`f` 和 `g` 在 0 到 999 上**逐点完全相等**，但它们在 x = 1000 处分道扬镳。任何"测了 1000 次就下结论"的推理，在这一步就已经错了。这就是"验证 n 个点 ≠ 证明恒等"的最小反例。

**实验二（工程版）：10 万次随机测试全过，程序照样会崩。**

```python
import random
random.seed(1)

def average(xs):
    return sum(xs) / len(xs)

# 随机测试：长度从 1 到 100，10 万次，全部通过
passed = 0
for _ in range(100000):
    n = random.randint(1, 100)                 # ← 生成器保证 n ≥ 1
    xs = [random.uniform(-1e6, 1e6) for _ in range(n)]
    assert abs(average(xs) - sum(xs) / n) < 1e-6
    passed += 1
print("随机测试通过次数:", passed)             # 100000

# 但规格是"对任意列表 xs 求平均"，它没说 xs 非空
try:
    average([])
except ZeroDivisionError as e:
    print("空列表 ->", type(e).__name__ + ":", e)
```

**这个 bug 逃过了 10 万次随机测试**，因为生成器只产生长度 ≥ 1 的输入。**随机测试的强度完全取决于生成器的设计。** 要用形式化验证抓它，你只需要写一条前置条件 `xs ≠ []`——机器会立刻在所有输入上把这件事说清楚。

**实验三：动手用一次证明器。** 打开 [Lean 在线编辑器](https://live.lean-lang.org/)，粘进这几行点运行：

```lean
-- 命题：0 + 1 + 2 + ... + n = n * (n + 1) / 2
example (n : ℕ) : 2 * (∑ k in Finset.range (n + 1), k) = n * (n + 1) := by
  sorry
```

按 `Ctrl` + `Enter`（或让编辑器自动补全），让 Lean 自己把 `sorry` 替换成它找到的证明。**这就是形式化验证最直观的样子：你写清命题和可用引理，机器负责把剩下的缝隙补上。** 顺便把等号改成不等号再试一次，看它如何精确地告诉你错在哪一步。

## 8. 自测

**第 1 题**　形式化验证和测试的根本区别是什么？请用第 7 节的"多项式"实验具体说明。

> **答案**　测试给出的是「某些输入下没出错」——一个有限的经验事实；形式化验证给出的是「**所有**输入下都满足这条性质」——一个数学定理。实验一里，f 和 g 在整数点 0 到 999 上**逐点完全相等**，1000 个测试全过，但 f(1000) ≠ g(1000)，因为 g 多了一个因子 (x−0)(x−1)…(x−999)。任何"测了 1000 次就下结论"的推理在这里都失效了。形式化验证能处理这种情况，办法是换一套更省输入的语言：证明一条**归纳不变式**（如"第 i 轮后累加和等于前 i 项之和"），再证明每一步转移保持它——这样就覆盖了无限多个输入。

**第 2 题**　第27章说那份混淆电路的证明「除非哈希被攻破，否则零信息泄露」（第27章，chapter-27.md:209）。为什么证明必须这样写？如果一份形式化证明不写任何前提假设，意味着什么？

> **答案**　因为形式化验证只能证明"**在若干假设成立的前提下**，结论成立"，它无法证明假设本身为真。密码学里几乎所有关键结论都归约到计算困难性假设上（大整数分解困难、离散对数困难、哈希无碰撞），形式化验证可以把归约链条一直做到底、并且**机器检查每一环都正确**，但链条的起点是假设。所以「除非哈希被攻破，否则零信息泄露」正是这份证明的**结论部分**——它精确标出了保证的边界和攻击者应该从哪里下手，这份诚实反而是证明可信的标志。如果一份形式化证明不声明任何前提假设，那么要么它证明的是一个平凡命题（比如"程序做的事就是规格写的"），要么它把假设偷偷藏在了规格里——后者更危险，因为读者会以为它是无条件的保证。

**第 3 题**　第27章 211 行穆的做法（让 AI 读论文自写实现，再让新实例与原版并排比对）与形式化验证是什么关系？两者各自能保证什么、不能保证什么？

> **答案**　穆的做法是**差分测试（differential testing）**，与形式化验证互补而非替代。差分测试问的是「这两个独立实现对同一输入会给出相同结果吗」，它**不需要知道程序"应该"做什么**，只需要一个参考实现；形式化验证问的是「这段代码在所有输入下都满足性质 P 吗」，它必须先有人写出 P。差分测试的强项是它**不需要规格**，所以能立刻用在刚写出来、还没有规格的新实现上；代价是它**不给出任何正面保证**——找不到反例并不证明没有反例。形式化验证的强项是**给出上界**（保证不出现某类错误），代价是**必须有人先写出正确的规格**，而且证明体量通常是代码的十倍到百倍。穆的方案还额外受限于"独立性"：如果 AI 读论文和 AI 写实现共享同一个误解，差分测试就发现不了——所以他让"一个全新的实例"来比对，是在人为增加独立性，但这终究不是数学意义上的独立保证。CompCert 编译器正是同时采用两条路线：核心翻译是机械证明的，后端则用随机程序做差分测试与 GCC 对比。
