# 42 沙盒与状态回滚（Sandbox and Rollback）

> 「我把这个程序放进沙盒，还给它套了日志式文件系统：它上不了网，我随时能回滚到初始状态。」——**这一整套机制的全部目的，是让你敢在一个不可信的东西上试危险的操作。**

## 1. 它是什么

三个配套的工程机制：

- **沙盒**（sandbox）：把不可信代码关进一个**受限制的环境**里，让它能算、但不能碰你不想让它碰的东西。
- **日志式文件系统**（journaling file system，如 ext4 的 JBD2、NTFS 的事务日志）：**先写"我要做什么"，再做**。崩溃时靠日志恢复。
- **回滚**（rollback）：把系统状态恢复到某个已知的干净快照。

三者合起来提供同一个保证：

> **你可以安全地试错——因为试错了可以撤销，而且试错过程本身不会造成不可逆的伤害。**

## 2. 小说里它在干什么

第 19 章，泽要在一个 60GB 的大文件里重建数据，并运行一个不可信的程序。

> 「我把这个程序放进**沙盒**，还给它套了**日志式文件系统**：**它上不了网**，我随时能**回滚到初始状态**。所以不用担心隐私泄露——结果不满意，回滚重来就行。那为什么不试试？」
> ——第19章，chapter-19.md:247

**三个要素，一个不缺**：

| 要素 | 解决什么问题 |
| --- | --- |
| **沙盒** | 防止程序**对外通信**（"它上不了网"）——**数据不能外流** |
| **日志式文件系统** | 防止程序**破坏文件系统的完整性**——崩溃时能恢复 |
| **回滚** | 防止"**结果不满意**"——可以撤销重试 |

**必须注意到一个细节**：他说"不用担心隐私泄露"，靠的是**沙盒的断网**，而不是加密。**这是一种和书里其他地方不同的隐私策略**——不是"数据被加密所以泄露了也没用"，而是"数据根本没机会离开这台设备"。

## 3. 直觉

- **沙盒** = 孩子的playpen（有围栏，可以玩，但玩不到外面的东西）
- **日志式文件系统** = 记着"我现在正在做哪一步"的小本子
- **回滚** = 存档点（Game 的 save）

## 4. 原理

### 4.1 沙盒：能力（capability）而不是边界

有两种安全思路：

**（a）边界式（perimeter）**："内网可信、外网不可信"，用防火墙隔离。
- 问题：一旦被绕过（比如一个漏洞），整个系统失守。**它是"信任边界"模型。**

**（b）能力式（capability）**："给程序的能力最小化"。
- 问题：不是"它在哪里"，而是"**它能做什么**"。
- 一个沙盒程序**只有**它明确被允许的系统调用。

**现代沙盒（seccomp-bpf、AppArmor、Landlock、macOS Seatbelt、Windows AppContainer）都是能力式的**——它们限制的是"**能调用哪些系统调用**"，而不是"处于哪个网络区域"。

**"它上不了网"的现代做法**其实**不是断网，而是**：
- 沙盒里**不允许发起网络连接的系统调用**
- 或者**只允许连一个白名单上的目标**（比如只允许读写这块磁盘）

后者更精细：**你不必禁止网络，只需要禁止它把数据送到不该送的地方。** 这叫**代理式出口控制**（egress filtering）。

### 4.2 日志式文件系统：写前日志（Write-Ahead Logging）

**核心思想：先记账，再干活。**

传统做法（ext3 等）：直接改磁盘。崩溃 → 改到一半 → 损坏。
日志式做法（ext4、NTFS、XFS、APFS）：

1. **先**把"我要做这个操作"写入日志（journal），并**刷盘**（fsync）
2. **然后**才真正修改数据
3. 崩溃后：读日志 → 知道哪些操作做了一半 → 重做或撤销

**为什么叫"日志式"**：因为它像一本**记账流水**。会计行业的核心原则是"**先记后做**"（write-ahead），文件系统直接借用了这个思路。

**一个漂亮的性质**：日志可以在**几秒内**写完（因为只写"要做什么"，不写"做了什么"），所以性能损失可接受。

**与"回滚"的联系**：日志记录了"你做了什么"，所以你可以**反向撤销**它。这正是**撤销日志**（undo log）的思路——数据库的 ACID 事务、编辑器的 undo 栈、Git 的 reflog，全都是这个模式。

### 4.3 回滚：三个不同层次的"回到过去"

| 层次 | 技术 | 代价 | 适合 |
| --- | --- | --- | --- |
| **文件系统层** | 快照（ZFS、Btrfs、APFS）、卷影副本 | **低**（增量） | 整机回滚 |
| **虚拟化层** | 虚拟机快照、容器 checkpoint | 中 | 环境回滚 |
| **应用层** | 事务、undo log、Git commit | **高**（只能回滚这个应用的数据） | 数据库、编辑器 |

**书中用的是最后一层**（"回滚到初始状态"），因为它要跑的只是一个程序和一小块数据。

## 5. 关键参数与现实取值

| 技术 | 代表 | 关键机制 |
| --- | --- | --- |
| Linux 沙盒 | seccomp-bpf、Landlock、AppArmor | **限制系统调用**（能力式） |
| macOS | Seatbelt sandbox | 限制 Mach 端口与文件访问 |
| Windows | AppContainer、WDAC | 隔离 + 强制策略 |
| 语言级 | WebAssembly | **能力集在语言里显式定义**（WASI） |
| 容器 | Docker、gVisor、Firecracker | 命名空间隔离 + 用户态内核 |
| 日志式 FS | ext4（JBD2）、NTFS、XFS、APFS | 写前日志 |
| 快照 | ZFS、Btrfs、LVM | 写时复制（COW） |

**WebAssembly 在这里特别值得提**：它把"沙盒"做进了**语言规范本身**——Wasm 模块**默认就不能碰网络、文件系统、时钟**，除非宿主显式提供。这从设计上杜绝了"忘记加限制"这类人为失误，**是能力式安全最彻底的实现**。

## 6. 容易误解的地方

**误解一：「沙盒是安全的绝对保障。」**
**不是。** 沙盒是**减少攻击面**，不是**消除**。已知威胁：
- **沙盒逃逸**：利用内核/虚拟化的漏洞跑出沙箱。这是真实存在的重大漏洞类别（如 Chrome 沙盒逃逸、Windows 提权）。
- **侧信道**：即使不能联网，也能通过**时间、功耗、缓存**泄露信息（见 [19](../crypto/19-anonymity-set-and-side-channel.md)）。
- **"允许列表"写漏了**：权限列表写错一项，防线就破了。

**真实世界的经验**：沙盒必须**多层**（"纵深防御"），且要**默认拒绝、逐项放行**。

**误解二：「日志式文件系统能防住一切崩溃。」**
它防的是**崩溃和断电**，不是**逻辑破坏**。如果程序**成功地**（按规则）删除了你的文件，日志会忠实地记录"删除了"，然后帮你**确认**这个删除已完成。**回滚需要的是快照或 undo log，不是 journal。** 很多人在这一点上混淆：journal 是"**保证操作原子性**"，snapshot 才是"**能回到过去**"。

**误解三：「回滚就是重新安装一次。」**
**不同。** 真正的回滚要满足：
- **完整性**：回到的状态必须是**曾经存在过的、已知良好的**状态
- **有凭据**：怎么知道那个状态是"好的"？需要**事先记录验证过**（这就是"签入"作为开发实践的意义）
- **彻底**：回滚后，被回滚的系统**不能还持有"已经发生"的副作用**（比如已经发出去的邮件、已经转出去的钱）

**第三点是沙盒回滚最难的部分**——**"已经造成的外部影响是无法回滚的"。** 这就是书里第 19 章的隐写消息已经发出去之后，**没法"回滚"这个事实**的根本原因。

**误解四：「断网就安全了。」**
**只挡住了外传，没挡住本地泄露。** 日志、swap、崩溃转储、屏幕截图、打印机缓存都可能留下痕迹。**书中第 19 章真正用来防"数据被读出来"的是隐写——** 也就是说"别人截获了文件也读不出内容"，而沙盒只是防"它自己往外发"。**两层防护，各管一头。**

## 7. 自己动手试试

**A. 亲手模拟回滚。** 打开一个文本编辑器：
1. 输入一段重要内容
2. 随便乱改几十下
3. 用 undo 回滚到你想要的版本
4. 观察：**undo 栈记住了什么？** 它记住了"操作的逆操作"，还是"之前的内容"？

**观察结论**：很多编辑器（以及数据库、Git）记的是**逆操作**（undo log），这比**存全部历史**省空间。**这就是写前日志的思想在交互式工具里的体现。**

**B. 设计一个沙箱策略。** 假设你要运行一个**从网上下载的解压缩程序**。列出它**必须**能做和**绝对不能**做的事：

| 允许 | 禁止 | 理由 |
| --- | --- | --- |
| 读下载目录 | **写系统目录** | 防篡改系统 |
| 写指定解压目录 | **执行任何程序** | 防运行恶意载荷 |
| 占用 CPU/内存（有上限） | **发起网络连接** | 防外传数据 |
| | **读取其他目录** | 防窃取隐私 |

**然后回答**：如果这个程序需要解压出 `.exe` 文件怎么办？
> **这就是真实世界的难题**：你**必须**允许它写出可执行文件（否则解不了压），但那样它就可能执行。解决方案是**两阶段**：第一阶段只解压到隔离区，**人工/扫描确认后**才允许执行。**这正是所有应用商店和防毒软件的基本思路**——**能力式安全必然会碰到"必须给的能力成为漏洞"的问题。**

**C. 想清楚"什么不能回滚"。** 列出三件你**做了就回不去**的事：
> 参考：已发送的邮件、已支付的钱、已公开发布的内容。
> **这就是分布式系统的核心难题**：本地可以回滚，**外部世界的状态回滚不了**。所以数据库的分布式事务要花那么大代价去解决"跨系统的一致性"——**因为你已经无法假装什么都没发生了。**

## 8. 自测

**Q1.** 沙盒、日志式文件系统、回滚，三者分别防的是什么？为什么需要三个而不是一个？

> **答案**。①**沙盒防"对外泄露/破坏"**：限制程序的能力（尤其是网络、文件系统），让它不能把数据传出去、不能碰不该碰的东西。②**日志式文件系统防"崩溃导致的损坏"**：通过写前日志保证每个操作要么完整完成、要么完全没做（原子性）。③**回滚防"做错了"**：把状态恢复到已知的良好快照。
> **三个防的是三种不同的失败**：①是"程序是恶意的"；②是"系统崩溃了"；③是"我做错了决定"。
> **只用一个不够**：没有沙盒，程序可能在你发现之前就把数据发出去了；没有日志，崩溃可能让你连"回滚到哪里"都不知道；没有回滚，你只能小心翼翼不敢试错。

**Q2.** 为什么说"断网"只是半拉子隐私保护？

> **答案**。因为"上不了网"只挡住了**外发**这一条路径。数据仍可能通过其他途径泄露：日志文件、swap、崩溃转储、屏幕、打印机、其他程序读取同一块内存。
> 更根本的是，**"数据离开了设备"和"数据被读懂了"是两个不同的问题**。断网解决前者，解决不了后者。书中真正用来防"被读懂"的是**隐写**（第 19 章）——也就是说：即使文件被截获，内容也读不出来（因为它是**被隐写编码过的健康数据**）。
> **正确的组合是：沙盒（防外发）+ 隐写/加密（防被读懂），两层各管一头。**

**Q3.** 为什么说"回滚"在分布式系统里是最难的？

> **答案**。因为**回滚只对"本地状态"有效**。一旦你做了**对外产生副作用**的操作（发出邮件、支付了钱、发布了内容、被别人看到了），**那个副作用就无法撤销**——外部世界已经变了。
> 所以分布式系统的"回滚"实际上必须是**补偿事务**（saga 模式）：不是"撤销已发生的事"，而是"**再做一件相反的事**"来抵消。而补偿事务本身也可能失败，于是需要最终一致性的设计。
> **这是本书里一个隐藏的重要教训**：第 19 章那个隐写消息一旦发出去，就再也收不回来了——**这是任何"试错可回滚"承诺的边界。**
