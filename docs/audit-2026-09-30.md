## 0. 总体判断

这套流水线的**设计**是可靠的：结构与文字彻底分离、片段级校验、成品自检、CI 闸门、术语表统一——
每一层都比一般 AI 译制工程扎实。产物也是干净可复现的：全新 clone 跑完两个构建脚本，
`git status` 为空（与提交产物逐字节一致）；32 章、4808 片段、56 图的数字全部对得上。

但这一轮审计暴露的问题集中在一个模式上，与 `docs/lessons.md` §6 上一轮的结论**恰好互为镜像**：

> 上一轮修的是「检查不会响」；这一轮暴露的是「**检查只在特定条件下才响**」。

具体表现为三类：

1. **闸门有条件地自我关闭**——`verify_extract`、三个 `qa_site` 结构检查在 CI 里永远跳过，
   而 `qa_site` 的成功文案仍然宣称检查了它们；
2. **闸门只看一面**——`qa_site` 的全部结构保真检查只对**英文栏**做，中文栏删表格、删插图、删色条一律放过；
3. **闸门只做全局、不做局部**——「不得残留英文」只在整段零中文时生效，于是「中文段落里混入整句英文」
   这类最常见的失败形态 100% 逃逸。

翻译实现本身的完成度很高（术语、数字、忠实度、语感都经得起抽查），但有 **6 处已经进入发布产物**的具体错误，
其中 1 处是把编辑性「译者注」印进了小说正文、且印在角色台词的引号内部。

## 1. 严重问题清单（按修复优先级）

### P0-1　`validate_translation` 对空片段零检查——漏译一整段不会被发现

`pipeline/validate_translation.py:151-168`

「疑似未翻译」检查的前提是 `if not re.search(r"[\u4e00-\u9fff]", body):`，
而空 body 走进 `symbol_ok = not words`（L166）→ 判定合规 → 放行。脚本从不比较片段长度或非空性。

反向注入实测（ch01，真实代码，非模拟）：

```
[PASS(漏过)] 清空一整段正文          （c01-s0023 → ""）
[PASS(漏过)] 把两段并成一段、另一段清空
[PASS(漏过)] 用上一段文字复制充数
```

三种都是 `translations/zh/*.zh.json` 的真实数据事故形态。对照 `pipeline/prompts/translate.md:67`
只要求译者「自己再通读一遍全文，确认没有漏译」——脚本不查这一项，但 CI 把 `validate_translation`
列为部署闸门之一，`OK chNN` 会被读成「本章没问题」。

**修法方向**：加一条硬检查——源片段 `text.strip()` 非空而译文 `strip()` 为空即报错；
另可对译文长度相对源长度的偏离设阈值告警。

### P0-2　「不得残留英文」只在整段零中文时生效

`pipeline/validate_translation.py:151`（`if` 把整段英文检测圈在里面）

`pipeline/prompts/translate.md:44` 写的是绝对规则「不得残留英文」，但脚本只在**整段没有中文**时才检查。
含中文的段落里，英文完全不受任何约束。反向注入实测：

```
[PASS(漏过)] 中文段中混入一整句未译英文
             「格拉迪亚斯立刻明白要做什么。He was not sure what to do.」
[PASS(漏过)] 专名/术语回退成英文
             「格拉迪亚斯立刻明白。作为 Veridian citizen，他被 crypto sortition 抽中。」
```

第二条尤其值得注意：术语表里 `Veridia → 维里迪亚` 是硬规定，译文回退成 `Veridian` 也不报错。

**影响**：这是 AI 逐章翻译最常见的失败形态，也是 prompt 声明为硬性、而脚本只做部分实现的唯一一条。

**修法方向**：把拉丁词扫描提到 `if` 之外，对 `strip_tags()` 后的全部正文检查；
不在术语表/词表/允许清单内、且不属于合法 conlang 上下文的拉丁词报 WARN 或 ERROR。

### P0-3　`qa_site` 的结构保真检查只覆盖英文栏，中文栏随便坏

`pipeline/qa_site.py:208, 216, 217, 226-227`

布局容器子项序列、`table/tr/td/th/blockquote/li` 计数、终端面板计数、插图计数
——全部只取 `pane_text(text, "en")`；中文栏只有一条长度下限。

反向注入实测（真实 `qa_site.py`，chapter-01）：

```
[PASS(漏过)] 中文栏删掉一张插图
[PASS(漏过)] 中文栏删掉一个表格
[PASS(漏过)] 中文栏删掉整个 flex 布局容器
[PASS(漏过)] 中文栏删 5 段正文（仍在长度阈值内）
[PASS(漏过)] 中文栏颜色全部丢失（说话人颜色失效）
[PASS(漏过)] 中文栏内容重复一次
```

对照能拦住的：

```
[FAIL(拦住)] 清空中文栏大部分文字  → 中文栏疑似缺失（中文 2253 字符 / 英文 21153 字符）
[FAIL(拦住)] 中文栏注入英文正文  → 缺少 id="pane-zh"
```

**影响**：`docs/pipeline.md:108-113` 把这些检查列为「布局与结构保真」的主要防线，
实际保护的是对照栏而不是译文。中文栏的颜色条（区分说话人的非颜色线索）整条链路失效也无人报警。

**修法方向**：把 `struct_counts` / `DEVICE_RE` / `out_fig` 三项同样对 `pane-zh` 跑一遍；
颜色 span 数量可加「中文栏与英文栏的 `color:#` span 计数应当相等」这一条。

### P0-4　`verify_extract` 与三个 `qa_site` 结构检查在 CI 里永远跳过，成功文案却说检查了

`pipeline/verify_extract.py:140-142`、`pipeline/qa_site.py:190-193`

`README.md:81` 写「以上校验全部接在 `.github/workflows/pages.yml` 的发布流程里：任一项失败即中止部署」。
实际情况是 `sources/en/` 被 `.gitignore` 忽略，CI 的全新 checkout 里根本不存在该目录，于是：

- `verify_extract` 打印「上游原文不入库，跳过抽取还原比对」，**退出 0**；
- `qa_site` 跳过布局容器 / 结构计数 / 中文栏长度三项；
- 但 `qa_site.py:291` 的成功文案仍然是
  「结构自检通过（**含布局容器子项与结构计数保真**）」。

全新 clone 复现：

```
--- verify_extract ---
sources/en/html 不存在（上游原文不入库），跳过抽取还原比对      exit=0
--- qa_site ---
提示：sources/en/html 不存在（上游原文不入库），跳过布局容器/结构计数/中文栏长度三项检查
OK：32 章 + 主页 + 目录，结构自检通过（含布局容器子项与结构计数保真）   exit=0
```

这是 `docs/lessons.md:94-95` 上一轮总结的「一个永远全红的检查同样没有用」的**镜像版本**：
一个永远不检查的检查，同样没有用——而且还对外宣称检查了。

**修法方向**（三选一或组合）：
1. 把「上游原文缺失」显式化为 `sys.exit(2)`，除非显式传 `--allow-missing-source`；
2. 把每章 `norm(original_text(ch))` 的 sha256 摘要入库，CI 无需原文即可比对；
3. 至少让 `qa_site` 的成功文案反映实际执行了哪几项。

`pipeline/merge_terms.py:84-85`

4 条术语冲突是各章 `new_terms` 里的陈旧残留（正文已由 `fixups.json` 修对，JSON 没同步），
但退出码恒为 1：

```
  ! chapter-04.zh: MU GU GEI FA 既有「五十提克」 vs 本章「五十嘀嗒」
  ! chapter-07.zh: symbol 既有「符记」 vs 本章「符」

  ! chapter-08.zh: prediction score 既有「预测分数」 vs 本章「预测分」
```

`README.md:35` 给的复现链是：

```bash

```

`&&` 短路 ⇒ **`normalize_zh.py` 永远不会执行**。照 README 走一遍第 3 步会静默停在术语合并上。

其中第 1 条是**术语表里的真错值**，且已经扩散到生成的文档：

```json
{"en":"MU GU GEI FA","zh":"五十提克","kind":"conlang","note":"倒计时播报（理解参考：五十嘀嗒）"}
```

- `docs/glossary.md:605` 同样写着 `| MU GU GEI FA | 五十提克 |`；
- 正文实际写的是阿拉伯数字：`c04-s0087`「50嘀嗒后开始」；

另注：`merge_terms.py:81-85` 是**先写 glossary.json 与 glossary.md，再 `sys.exit(1)`**，
与 `docs/pipeline.md:131` 读起来的「有冲突则 exit 1」（先判断后拒绝）相反。

**修法方向**：清掉 4 章 `new_terms` 的陈旧项（或让 `merge_terms` 在 `zh` 已被 alias/fixup
归一化到 canonical 时视作一致）；把 `MU GU GEI FA` 的 `zh` 改成与正文一致的写法；
冲突时先 exit 再写盘；README 的命令链改用 `;` 或分两行。

### P0-6　正文里混入了编辑性「译者注」，且印在角色台词的引号内部

`translations/zh/chapter-28.zh.json` `c28-s0049` → `book/snowmoon-zh.md:7823` →
`book/chapters/chapter-28.md` → `book/site/read/chapter-28.html`

```
EN: "...the exploits will work great against the damaged drone that you guys
     managed to recover from Northshore two months ago. You can take the credit for them."
ZH: "……但这些漏洞用在两个月前你们从北岸弄回来的那架受损无人机上，会很灵。
```

1. 直接违反 `pipeline/prompts/translate.md:43` 的硬性规则「不得在正文里写译注或括号说明原文」；
2. 它落在**穆的台词引号内部**（`<span style="color:#00bc96">"…会很灵。（译者注：…）功劳都算你的。"</span>`）——

**修法方向**：整段删除，保留纯译文；这个存疑点若要记录，放进 `docs/` 或 `reviews/`，不留在小说里。

### P0-8　第 3 章表格有一处 `<td>` 嵌套错误，已进入不可变的骨架与上线站点

`pipeline/extract.py:188-195`（`handle_endtag` 找不到匹配开标签时静默 `return`，无告警）

上游 `sources/en/html/chapter-3.html` 本身有一个未闭合的 `<td>`：

```html
<td><ul><li>Cleanup</li>…</ul>
      <td><button> Learn more </button></td>
```

`html.parser` 不是 HTML5 树构造器，未闭合的 `<td>` 不会被自动修复，于是抽取产物变成：

```html
<!-- sources/work/chapters/chapter-03.json 的 c03-b0054 -->
<tr><td>Environment</td><td><ul>…</ul><td><button>Learn more</button></td></td></tr>
```

第三个 `<td>` 嵌在第二个里面；同一张表的其他行都是三个平级单元格。
该错误原样出现在 `book/site/read/chapter-03.html`（浏览器会自动纠错，所以能正常显示，
但这是非法嵌套）。

**没有任何闸门能看见它**：`verify_extract` 只比文本；`qa_site` 数 `<td>` 数量——嵌套没有改变数量，仍是 3 个。

这正是 `docs/pipeline.md:27-28` 声称要杜绝的那一类（「杜绝翻译过程中结构漂移（表格塌陷…）」），

**修法方向**：`b.feed(body)` 之后做一次逐标签开闭配平检查，未配平即 `SystemExit`（与 SVG 守卫同款），
或至少逐次告警。
